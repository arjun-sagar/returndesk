# ReturnDesk

ReturnDesk is a returns desk for a small online store. A support agent raises a return request against an order, searches and reviews requests, adds permanent notes, approves (with a resolution) or rejects a request, completes it, corrects its details while it is still undecided, and takes eligible requests off the desk without destroying the record.

It is a full-stack Next.js app with a hand-written JSON API and a PostgreSQL database. Every business rule is enforced on the server (and the key invariants again in the database), so the rules hold even when the API is called directly rather than through the UI.

## Features

- **Raise a request**: customer name, email and/or phone (at least one), order number, item SKU, item name, quantity (1-999) and one of five reasons (`Damaged`, `Wrong Item`, `Size Issue`, `Not As Described`, `Changed Mind`). The reference (`RD-000001`, `RD-000002`, ...) is generated by the database and can never be supplied by the client.
- **Find requests**: search (reference, customer name, email, phone, order number), filter by status and by reason, sort (newest, oldest, recently updated, customer A-Z/Z-A, status in lifecycle order) and page (10/20/50 per page). All of it runs in one SQL query on the server; the search box is debounced (350 ms) and Enter applies it immediately. The list state lives in the URL, so it can be bookmarked and the Back button works.
- **Work a request**: a detail page with all fields, status, resolution and refund amount, timestamps and every note in chronological order.
- **Lifecycle**: `Open` -> `In Review` -> `Approved` -> `Completed`, or `In Review` -> `Rejected`. Approving needs a resolution (`Refund`, `Replacement` or `Store Credit`); a refund needs an amount greater than zero.
- **Notes**: append-only. There are no update or delete endpoints, and a database trigger blocks `UPDATE`/`DELETE` on notes even from raw SQL.
- **Edit**: customer and item details can be corrected only while the request is `Open` or `In Review`.
- **Remove from desk**: soft removal (`removed_at`), allowed only for `Open` or `Rejected` requests. The row and its notes stay in PostgreSQL; the request disappears from the list and from every endpoint.
- **Only legal actions are offered**: the API returns `allowedActions` with each request and the UI renders its buttons only from that. The server still re-checks everything.
- **UI states**: loading skeletons, refetch ("Updating...") state, error state with Retry, empty states ("no requests yet" / "no requests match these filters"), a page-out-of-range state, a not-found state for missing or removed requests, disabled buttons while an action is pending, and inline confirms instead of `window.confirm`. Layout targets 375 px width and up (table on `md` and wider, cards below).

Added beyond the brief (the assignment invites this): database-level defence in depth (CHECK constraints, a partial unique index, triggers against hard deletes and note edits), a non-mutating smoke script that works against any URL, and API integration tests that include parallel-request race checks.

## Stack and architecture

| Layer | Choice |
|---|---|
| Framework | Next.js 16 (App Router), React 19, JavaScript (no TypeScript) |
| Backend | Next.js Route Handlers under `app/api/**` on the Node.js runtime (no Express) |
| Database | PostgreSQL through `pg` (node-postgres) with one shared `Pool`; explicit parameterised SQL, no ORM or query builder |
| Hosted database (planned) | Neon (pooled connection string) |
| Styling | Tailwind CSS v4, light theme only |
| Validation | Hand-written pure functions in `lib/validation.js`, used by both the API and the browser forms |
| Tests | Vitest |
| Deployment (planned) | Vercel |

How the pieces fit:

```
Browser (client components)  --fetch-->  app/api/**/route.js  (thin: parse id/body, call service, wrap errors)
        |                                        |
        | shared pure code                       v
        +--> lib/validation.js          lib/request-service.js  (ALL SQL + transactions)
        +--> lib/constants.js                    |       \
                                                 |        +--> lib/rules.js   (business rules, pure)
                                                 v
                                            lib/db.js  (pg Pool)  -->  PostgreSQL
```

- `app/requests/**` pages are thin server components; the interactive screens are client components in `components/` that call the app's own JSON API (the same API anyone can test directly).
- `lib/rules.js` holds every business rule as pure functions. `lib/request-service.js` is the only module with SQL; it runs the rule checks inside transactions with row locks (`SELECT ... FOR UPDATE`).
- `lib/db.js`, `lib/http.js` and `lib/request-service.js` are server-only by convention: no client component imports them, and `DATABASE_URL` has no `NEXT_PUBLIC_` prefix, so it never reaches the browser.
- Persistence: all application data is in PostgreSQL, configured through `DATABASE_URL`. Nothing is stored in memory, files or browser storage, so data survives a server restart.

## Quick start (clean Mac)

Prerequisites:

- **Node.js >= 22.9** (the `db:*` scripts use `node --env-file-if-exists`, which needs it; `package.json` declares `"engines": { "node": ">=22.9" }`). Check with `node -v`.
- **npm** (ships with Node).
- **PostgreSQL 12 or newer** running locally, with `psql` on your `PATH`. The schema uses generated columns, which need PostgreSQL 12+. The project was developed against Homebrew PostgreSQL 14. If you have none: `brew install postgresql@14 && brew services start postgresql@14` (Homebrew prints the `PATH` line to add).
- Internet access for `npm install`. `app/layout.js` uses `next/font/google`, so `npm run build` also downloads the Geist fonts from Google Fonts.

Steps:

```bash
# 1. Create a local database role and database (local development only).
psql -d postgres -c "CREATE ROLE returndesk WITH LOGIN PASSWORD 'returndesk_local_dev';"
psql -d postgres -c "CREATE DATABASE returndesk_dev OWNER returndesk;"

# 2. Get the project and install dependencies.
cd returndesk
cp .env.example .env.local
# Put the same password into .env.local (macOS sed):
sed -i '' 's/CHANGE_ME/returndesk_local_dev/' .env.local
npm install

# 3. Create the tables and load the demo data.
npm run db:setup

# 4. Start the app.
npm run dev
```

Open <http://localhost:3000>; it redirects to `/requests`. Choose your own role password if you prefer, and use the same one in `.env.local`. If the role or database already exists, reuse it; do not drop anything you did not create.

`.env.local` is git-ignored; only `.env.example` (placeholders) is committed. For a hosted database and Vercel deployment see [Setup.md](Setup.md) and [DB.md](DB.md).

## Database commands and seed data

| Command | What it does | Safe to re-run? |
|---|---|---|
| `npm run db:migrate` | Applies the pending `db/migrations/*.sql` files in filename order, each in its own transaction together with its row in `schema_migrations`. Prints applied/skipped. | Yes |
| `npm run db:seed` | Inserts the demo data **only if `return_requests` is completely empty** (removed rows count as data); otherwise prints that nothing changed. | Yes |
| `npm run db:setup` | `db:migrate` then `db:seed`. This is the "build from empty" command. | Yes |
| `npm run db:reset -- --confirm` | **Destructive.** Drops `request_notes`, `return_requests`, `schema_migrations` and the `forbid_row_change()` function, then migrates and seeds again. | Deletes all data |

**Warning: `db:reset` deletes every request and note. Never point it at production.** It refuses to run without `--confirm`, and refuses any non-local host (anything other than `localhost`, `127.0.0.1`, `::1` or a local socket) unless `ALLOW_REMOTE_RESET=I_UNDERSTAND_THIS_DELETES_DATA` is also set. All the scripts print the target as `host/database` (never the password) before doing anything.

The seed (`scripts/seed-data.js`, written by `scripts/seed.js` in one transaction that first takes `LOCK TABLE return_requests IN SHARE ROW EXCLUSIVE MODE`) creates **38 requests: 36 visible and 2 removed**:

- Visible requests per status: Open 8, In Review 7, Approved 7, Rejected 7, Completed 7. Within each status the five reasons cycle, so every status x reason pair appears.
- The 14 Approved/Completed requests carry a resolution: Refund 6 (with amounts above zero), Replacement 4, Store Credit 4. Replacement and Store Credit rows have no amount.
- 37 notes on 21 requests, 12 of those requests with two or three notes, in strictly increasing time order after the request was created.
- Two rule-3 demonstrations: an earlier Rejected request and a newer Open request for the same order + item, and an earlier Completed request with a newer Open one.
- Two removed requests (one Open with two notes, one Rejected): they stay in the database but never appear in the API.
- No two live, non-removed requests share an order + item.
- Timestamps are relative to the moment you seed (spread over roughly the last 45 days), but the content is deterministic.

(These figures come from reading and evaluating `scripts/seed-data.js`; the seed's own output after a run prints the totals, per-status and per-reason counts and the notes count.)

## API

Base path `/api`. JSON in, JSON out. Every `/api` response is JSON, including unknown routes (404) and unsupported methods (405). The numeric `id` is used in URLs; the human-readable `reference` (`RD-000042`) is shown to users and is searchable.

| Method and path | Purpose | Success |
|---|---|---|
| `GET /api/requests` | List with `q`, `status`, `reason`, `sort`, `order`, `page`, `pageSize` | `200 { data: [...], meta }` |
| `POST /api/requests` | Create a request | `201 { data }` with `Location: /api/requests/{id}` |
| `GET /api/requests/{id}` | Detail, with `notes` and `allowedActions` | `200 { data }` |
| `PATCH /api/requests/{id}` | Edit any subset of the create fields while `Open` / `In Review` | `200 { data }` |
| `DELETE /api/requests/{id}` | Remove from the desk (soft), only `Open` / `Rejected` | `200 { data: { id, reference, removedAt } }` |
| `POST /api/requests/{id}/transitions` | Change status. Body `{ status, resolution?, refundAmount? }` | `200 { data }` |
| `POST /api/requests/{id}/notes` | Append a note. Body `{ author, body }` | `201 { data: { id, author, body, createdAt } }` |
| anything else under `/api/*` | - | `404 ROUTE_NOT_FOUND` |
| a known path with an unsupported method | - | `405 METHOD_NOT_ALLOWED` with an `Allow` header |

There are deliberately **no** note update/delete endpoints and no way to set `reference`. `DELETE /api/requests/{id}/notes/{noteId}` is just an unknown route (404).

**Create / edit body fields:** `customerName` (required, 1-100), `customerEmail` and `customerPhone` (optional, at least one required), `orderNumber` and `itemSku` (required; normalised by trimming and uppercasing; letters, digits and `# . _ / -` only, up to 40), `itemName` (required, 1-200), `quantity` (required JSON integer 1-999; strings such as `"2"` are rejected), `reason` (one of the five). Unknown fields are rejected with 400, not silently ignored: `reference` ("generated by the system"), `status`/`resolution`/`refundAmount` on create or edit ("use POST /api/requests/:id/transitions"), `id`/`createdAt`/`updatedAt`/`removedAt` ("read-only"). `PATCH` needs at least one field; the "email or phone" rule is re-checked on the merged record, so you cannot clear both contacts.

**Transition body:** `status` must be one of the five statuses. `resolution` and `refundAmount` are accepted only when `status` is `Approved`. `refundAmount` is a number or string with at most two decimals, at most 1,000,000, and is stored and returned as a string such as `"1499.00"` (currency INR).

**List query:** `q` (up to 100 characters), `status`, `reason` (exact values), `sort` in `createdAt | updatedAt | customerName | status` (default `createdAt`), `order` in `asc | desc` (default `desc`), `page` (>= 1, default 1), `pageSize` (1-100, default 20). Invalid values are a 400; unknown query parameters are ignored. A page beyond the end is a `200` with `data: []` and the correct `total`.

### Success envelope

```json
{ "data": { "id": 7, "reference": "RD-000007", "customerName": "...", "status": "Open", "refundAmount": null, "...": "..." } }
```

Lists add `meta`:

```json
{ "data": [ { "...": "..." } ],
  "meta": { "page": 1, "pageSize": 20, "total": 36, "totalPages": 2,
            "sort": "createdAt", "order": "desc", "q": null, "status": null, "reason": null } }
```

Request objects contain `id, reference, customerName, customerEmail, customerPhone, orderNumber, itemSku, itemName, quantity, reason, status, resolution, refundAmount, createdAt, updatedAt`. The detail endpoint adds `notes` (oldest first; each `id, author, body, createdAt`) and `allowedActions`: `{ transitions: [...], canEdit, canRemove, canAddNote }`. Timestamps are ISO 8601 strings. (The values above are illustrative.)

### Error envelope

```json
{ "error": { "code": "INVALID_STATUS_TRANSITION",
             "message": "A request cannot move from Open to Completed. Allowed next steps: In Review.",
             "details": { "from": "Open", "to": "Completed", "allowed": ["In Review"] } } }
```

`details` is present only when there is something useful to say (for `VALIDATION_ERROR` it is `{ "fields": { "<field>": "<message>" } }`). Failed operations never return 2xx. Unexpected failures return a generic `INTERNAL_ERROR` message; SQL text, stack traces and connection strings are never sent to the client (the server logs only the method, path, error code and the first line of the message).

### Error codes

| HTTP | `code` | When | `details` |
|---|---|---|---|
| 400 | `INVALID_JSON` | Body is not valid JSON, or is not a JSON object | - |
| 400 | `VALIDATION_ERROR` | Missing/malformed/unknown fields, bad query parameters, malformed `id`. Also the fallback for a database rejection that slipped past validation (check violation, invalid text, numeric overflow) | `fields` (except the database fallback) |
| 404 | `NOT_FOUND` | The request does not exist **or has been removed** (all endpoints, notes included) | - |
| 404 | `ROUTE_NOT_FOUND` | Unknown `/api/*` path (including bare `/api`) | - |
| 405 | `METHOD_NOT_ALLOWED` | Known path, unsupported method | `allowed` |
| 409 | `INVALID_STATUS_TRANSITION` | The move is not in the status graph (including same-state moves and anything out of a final state) | `from`, `to`, `allowed` |
| 409 | `DUPLICATE_LIVE_REQUEST` | Create or edit would give one order + item a second live request | `orderNumber`, `itemSku`, `existingReference` (the fallback form has no details) |
| 409 | `REQUEST_LOCKED` | Edit attempted on an Approved, Rejected or Completed request | `status` |
| 409 | `REMOVAL_NOT_ALLOWED` | Remove attempted on an In Review, Approved or Completed request | `status`, `removableStatuses` |
| 422 | `RESOLUTION_REQUIRED` | Approving without a resolution | - |
| 422 | `REFUND_AMOUNT_REQUIRED` | `Refund` without an amount greater than zero | - |
| 422 | `REFUND_AMOUNT_NOT_ALLOWED` | `Replacement` / `Store Credit` with any amount (including 0) | - |
| 500 | `INTERNAL_ERROR` | Unexpected failure only | - |

The browser client (`lib/api-client.js`) additionally raises its own `NETWORK_ERROR`, `BAD_RESPONSE` and `UNKNOWN_ERROR` codes when the server cannot be reached or does not answer with the expected JSON; the API itself never sends those.

How the statuses are chosen: **400** means "you sent something malformed", **409** means "this conflicts with the record's current state", **422** means "well-formed approval that breaks the approval rule". Order of checks in a handler: id and body format (400) -> existence (404) -> state (409) -> approval rule (422). So `Open -> Approved` is always a 409, even with a perfect resolution.

## Business rules and where they are enforced

Each rule is checked in the shared pure rules module, applied by the service layer inside a transaction, and (where PostgreSQL can express it) backed by a database constraint.

| # | Rule | Rules module (`lib/rules.js`) | Service (`lib/request-service.js`) | Database |
|---|---|---|---|---|
| 1 | **Status flow.** Only `Open -> In Review`, `In Review -> Approved`, `In Review -> Rejected`, `Approved -> Completed`. `Rejected` and `Completed` are final. | `TRANSITIONS`, `canTransition`, `assertTransitionAllowed` (409 `INVALID_STATUS_TRANSITION`) | `transitionRequest` locks the row (`FOR UPDATE`), then asserts legality **before** the approval rule. The lock serialises concurrent changes: if approve and reject race, one wins and the other gets 409. | `return_requests_status_check` limits the *values* of `status`. The *graph* is not a database constraint (it is enforced in the service only). |
| 2 | **Approval needs a resolution.** `Refund` needs an amount > 0; `Replacement` / `Store Credit` must have no amount. | `normalizeApproval` (422 `RESOLUTION_REQUIRED`, `REFUND_AMOUNT_REQUIRED`, `REFUND_AMOUNT_NOT_ALLOWED`); format checks in `validateTransitionInput` in `lib/validation.js` (400) | `transitionRequest` calls `normalizeApproval` inside the transaction, so a failed approval leaves the request unchanged | `return_requests_resolution_check`, `return_requests_refund_amount_check`, `return_requests_resolution_status_check` (a resolution exists exactly when the status is Approved or Completed) |
| 3 | **One live request per order + item.** Live = Open, In Review, Approved. A new one is allowed once the earlier is Rejected or Completed. | `LIVE_STATUSES`; `normalizeCode` in `lib/validation.js` makes order number and SKU trimmed and uppercase | `createRequest` and `updateRequest` rely on the unique index, catch Postgres error `23505` and `toDuplicateError` turns it into 409 `DUPLICATE_LIVE_REQUEST` naming the existing reference. `lib/http.js` has a generic fallback for the same error. | Partial unique index `return_requests_one_live_per_item` on `(order_number, item_sku)` `WHERE status IN ('Open','In Review','Approved') AND removed_at IS NULL`; `return_requests_order_number_check` / `return_requests_item_sku_check` force the normalised form |
| 4 | **Locked once decided.** Details can be edited only while Open or In Review; notes can still be added. | `EDITABLE_STATUSES`, `canEdit`, `assertEditable` (409 `REQUEST_LOCKED`) | `updateRequest` locks the row, asserts editable, re-checks the email/phone rule on the merged record, and updates only allow-listed columns | Not a database constraint (enforced in the service only) |
| 5 | **Removal never destroys the record.** Only Open or Rejected may be removed; the request disappears from the list and detail. | `REMOVABLE_STATUSES`, `canRemove`, `assertRemovable` (409 `REMOVAL_NOT_ALLOWED`) | `removeRequest` stamps `removed_at`. Every read and write path filters `removed_at IS NULL` (list, detail, edit, transition, remove and note creation), so removed requests answer 404 everywhere. | `return_requests_removal_status_check` (`removed_at` only with Open/Rejected); trigger `return_requests_no_hard_delete` blocks `DELETE`; `request_notes.request_id` is `ON DELETE RESTRICT`, so notes are never cascaded away |

Related guarantees:

- **Notes are append-only**: no endpoint changes or deletes a note, and trigger `request_notes_append_only` rejects `UPDATE`/`DELETE` on `request_notes` at the database level. `addNote` inserts in a single statement that only succeeds if the request exists and is not removed. Adding a note does not change `updated_at` (that column tracks the request's own fields and status).
- **Sort and search safety**: `sort` and `order` are validated against allowlists and then mapped to fixed SQL strings (`SORT_SQL`, `ORDER_SQL`); nothing from the client is interpolated into SQL. Search text is passed as a parameter and `%`, `_` and `\` are escaped so they match literally.
- **Ids**: a malformed `id` (for example `abc`, or one beyond the 32-bit integer range) is a 400 from `parseRequestId`, never a database error.

## Schema and indexes

Defined in `db/migrations/001_initial_schema.sql` (comments in the file explain why each constraint exists). `schema_migrations` is created by the migration runner.

- **`return_requests`**: `id` (`integer GENERATED ALWAYS AS IDENTITY`), `reference` (a `STORED` generated column: `'RD-' || lpad(id::text, GREATEST(6, length(id::text)), '0')`, with a `UNIQUE` constraint), customer fields, `order_number`, `item_sku`, `item_name`, `quantity`, `reason`, `status` (default `Open`), `resolution`, `refund_amount numeric(10,2)`, `created_at` / `updated_at` / `removed_at` as `timestamptz`.
- **`request_notes`**: `id`, `request_id` (foreign key to `return_requests`, `ON DELETE RESTRICT`), `author` (1-80), `body` (1-2000), `created_at`.
- Allowed values (status, reason, resolution) are `text` columns with `CHECK` constraints rather than Postgres `ENUM` types.
- Triggers: `request_notes_append_only` and `return_requests_no_hard_delete` (both call `forbid_row_change()`).

| Index | Purpose |
|---|---|
| `return_requests_one_live_per_item` (unique, partial) | Rule 3: one live, non-removed request per order + item |
| `return_requests_reference_key` (unique constraint) | References are unique |
| `return_requests_active_created_idx` `(created_at DESC, id DESC) WHERE removed_at IS NULL` | Default "newest first" desk listing |
| `return_requests_active_status_idx` `(status) WHERE removed_at IS NULL` | Status filter |
| `return_requests_active_reason_idx` `(reason) WHERE removed_at IS NULL` | Reason filter |
| `request_notes_request_created_idx` `(request_id, created_at, id)` | Reading one request's notes in order |

Search is a substring `ILIKE` over five columns and has no index on purpose (see [Choices.md](Choices.md)). Those indexes are intended for the queries named above; no query-plan or timing measurements were taken for this project.

## Design decisions and assumptions

The reasoning behind each choice, alternatives and trade-offs are in [Choices.md](Choices.md). The assumptions the assignment left open:

- **Currency is INR.** Money is `numeric(10,2)` (never floating point), carried through the API as a string (`"1499.00"`) and shown with `Intl.NumberFormat('en-IN', { currency: 'INR' })`. There is no multi-currency support.
- **No authentication; demo only.** The assignment does not ask for it. The "author" of a note is free text typed into the form.
- **Removed requests are invisible everywhere.** They disappear from the list and answer `404 NOT_FOUND` on every endpoint, including adding a note (the assignment says a removed request "can no longer be fetched"). They also **do not block** a new request for the same order + item: if they did, an Open request that was removed (and so can no longer be opened or closed) would block that item forever.
- **`Rejected` is reachable only from `In Review`**, exactly as the assignment's status diagram shows. `Open -> Rejected` is refused.
- **Item identity = normalised `order_number` + `item_sku`.** Both are trimmed and uppercased before saving, so `ord-1 ` and `ORD-1` are the same order; the database `CHECK` enforces that stored values are in normal form. The item *name* is descriptive text and is not part of the identity. SKUs are assumed to be stable codes.
- **Contact rule:** at least one of email or phone is required, on create, and still holds after an edit (checked on the merged record, and also by a database `CHECK`).
- **"Details" that may be edited** while Open / In Review: every create field (customer name, email, phone, order number, item SKU, item name, quantity, reason). Status, resolution, refund amount and reference are never editable through `PATCH`. An edit that would collide with another live request for the same order + item is refused with 409.
- **Ids are numeric** (`integer` identity) in URLs and APIs; the `RD-` reference is for people.
- **Notes can be added in any status** (Open, In Review, Approved, Rejected, Completed) but not on a removed request.
- Name and item text fields are whitespace-normalised (trimmed, runs of spaces collapsed); note bodies keep their internal line breaks.

**Known limitations:**

- No authentication, roles or audit trail. Status changes are not logged to a history table; only the current status and `updated_at` are stored (agents record context in notes).
- Edits are last-write-wins: the row lock prevents a corrupted state, but a form opened earlier can overwrite a newer edit of the same fields (there is no version or ETag check).
- Search is an unindexed substring `ILIKE` over reference, name, email, phone and order number. Fine at desk scale; it would need a trigram index for large data.
- Pagination uses `LIMIT`/`OFFSET`, which gets slower for very deep pages.
- Money is a single currency (INR). Refund amounts are capped at 1,000,000.
- Sequence gaps: references come from an identity sequence, and an insert that fails (for example a refused duplicate) still consumes a number, so references can skip values.

**Next steps:** deploy (Neon + Vercel) and run the smoke script against the live URL; add the live URL and hours to this file; add browser-level end-to-end tests; add a status-history table and authentication if this were ever used beyond a demo; add a trigram index if search volume grows.
